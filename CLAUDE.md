# natyv — Architectural Reference

This file exists so a fresh session in this repo has the load-bearing "why" behind natyv's design without needing to re-derive it or search external memory. It covers *decisions and rationale*, not history — see `README.md` for the milestone timeline.

**Post-split scope note (2026-08-31):** natyv's original monorepo (`natyv-io/natyv`, now archived) was split into four real repos — `natyv-io/shared` (just `Config`, the `conf.natyv.json` schema/parser, imported by both repos below as a named Zig module `@import("Config")`, not a relative file), **`natyv-io/core`** (this repo — the runtime), `natyv-io/cli` (the `natyv` CLI: `prepare`/`build`/`init`/`get`, the `.ntx`/styling/binding-generator *codegen* tooling, `ntx-lsp`, editor extensions, AppImage packaging), and `natyv-io/sdks` (guest-language SDKs, e.g. `sdk/go`). This file is kept as ONE copy, living here in `core`, since most of the content below (widget system, styling, threading model, multi-window, TCP/TLS) is genuinely about the runtime. Sections describing CLI-only concerns (**"CLI build flow"**, the binding generator's CLI surface, LSP editor tooling, AppImage/Windows-icon packaging) describe real, still-accurate design decisions, but the actual source files they reference now live in `natyv-io/cli`'s own repo, not here — treat file paths in those sections as historical/cross-repo context, not a claim about what's in this checkout. See the `natyv-repo-split-plan` memory for the split itself, and `natyv-tcp-tls-host-function` memory for how the split was discovered (a stale local checkout was still tracking the archived monorepo well after the split shipped) — check which repo a local `natyv` checkout's `origin` actually points at before trusting file paths against it.

## Vision

natyv is a native desktop app runtime: app logic runs as a WASM guest module (via [Extism](https://extism.org)) inside a native host that natyv provides — no bundled browser engine, no DOM. The host owns the window/render loop (SDL3-backed); the guest declares its UI and business logic and talks to the host through capability-scoped host functions.

**Positioning** (two real claims, both honestly caveated): leaner than Electron on memory (no bundled Chromium, no DOM/CSSOM, no GC-heap-stickiness creep), and more language-agnostic than Tauri (Extism/WASM is the interop boundary, not one native language) — real, but smaller a differentiator than it feels from the inside, since most Tauri apps already write UI in JS/HTML and only touch Rust for backend commands. Real non-zero cost: `libextism` (Wasmtime + Cranelift) is a genuine ~20MB dependency. A real GitHub issue on Tauri's own repo shows Tauri using *more* memory than Electron in 2 of 3 real-app measurements (naive RSS summation double-counts Chromium's shared pages) — the "Rust backend = lean app" popular claim doesn't hold up, which is the exact tax natyv's no-DOM architecture is built to avoid regardless of backend language.

## Toolchain

Zig 0.16.0, Extism runtime 1.30.0 (see `build.zig.zon`). Policy: pin to whatever's genuinely latest when a baseline is established, then hold N-1 behind current until forced to bump — Zig's build system and package-manifest format are still churning between releases. **Extism itself is a different story, per Quinn's own read of the company's real trajectory (2026-08-24): they've largely moved off actively focusing on the product/WebAssembly at all, so new Extism releases are unlikely going forward** — the N-1-behind-current policy is effectively moot for this specific dependency; don't expect or chase frequent Extism version bumps, and don't assume active upstream maintenance if something ever needs a fix there.

**Zig's test runner includes every `test` block in every file it actually analyzes while compiling a given root, not just the root file's own tests** -- confirmed empirically 2026-08-24 while adding `src/ntx/Expose.zig` (its own test binary also re-runs `Parser.zig`'s 10 tests, since `Expose.zig`'s tests actually call into `Parser`). Real, not a bug -- expect a build-target's own test count in `zig build test`'s summary to sometimes exceed that file's own `test` block count when it meaningfully uses another file's declarations.

**SDL3 is vendored via the real Zig package `allyourcodebase/SDL3` (pinned `1.0.1+3.4.14` in `build.zig.zon`), not Homebrew** — confirmed and switched 2026-08-24, replacing the `sdl3Prefix()`/`-Dsdl3-prefix`/`NATYV_SDL3_PREFIX` machinery (removed). Real, necessary fix, not a preference: Homebrew's SDL3 install ships no static archive at all (`ls $(brew --prefix sdl3)/lib` — only `libSDL3.0.dylib`), so a Homebrew-linked `natyv-core` could never be genuinely self-contained; an end user without SDL3 installed would hit "library not loaded" at launch. `allyourcodebase/SDL3` compiles real upstream SDL3 source via Zig's own C toolchain and is static by default. `build.zig`'s `linkNatyvDeps` now does `const sdl_dep = b.dependency("sdl", .{.target = module.resolved_target.?, .optimize = module.optimize.?}); module.linkLibrary(sdl_dep.artifact("SDL3"));` instead of `linkSystemLibrary` + brew include/lib paths — `linkLibrary` propagates the dependency's own public include path automatically, so `src/c.zig`'s existing single-`@cImport`-boundary architecture (the one place `SDL3/SDL.h` gets `@cImport`ed, used everywhere else in the codebase) needed zero changes. Verified for real, not just "it compiled": `otool -L zig-out/bin/natyv-core` shows no `libSDL3` dependency at all (only Apple's own always-present system frameworks + the still-dynamic system `libsqlite3`), 40/40 build steps and 502/502 tests still pass, and `examples/clay-fixture` launched and ran identically to before. **Real, confirmed side effect**: this pulls a real `zig-pkg/` local cache directory (SDL3's own transitive per-target dependencies, e.g. X11/Wayland protocol headers for its Linux config) into the project root — regenerable, ~376MB, added to `.gitignore` alongside `.zig-cache/`/`zig-out/`.

**Always measure natyv-core's binary size in `-Doptimize=ReleaseSmall`, never Debug -- confirmed 2026-08-27.** Quinn's own impression that vendoring SDL3 statically "bloated the binary by a good bit" was real but measured against the wrong build mode: in Debug, static-vendored SDL3 costs ~21MB over a Homebrew-dynamic-linked comparison build (90MB vs 68MB) -- but in `ReleaseSmall` (what `natyv build` actually ships), the same comparison shows only a ~2.2MB difference (25.8MB vs 23.5MB), since ReleaseSmall's optimizer dead-strips most of SDL3's unreferenced code that Debug keeps whole. The same pattern holds for sqlite's own build-time stripping (see "Capabilities are runtime-permission-gated..." below): its documented ~9.4MB Debug-mode saving drops to under 1MB in ReleaseSmall. **Lesson: any future "is X bloating our binary" question needs a real ReleaseSmall A/B measurement, not a Debug one -- Debug-mode deltas systematically overstate real shipped-binary impact by roughly 10x in both cases measured so far.** No further SDL3 size work is planned: the `allyourcodebase/SDL3` wrapper's own build.zig has no subsystem-level toggle (only static-vs-dynamic linkage) to compile out unused audio/joystick/haptic/camera/sensor code (natyv only ever calls `SDL_Init(SDL_INIT_VIDEO)`), and forking that wrapper for it would be ongoing maintenance for less savings than ReleaseSmall's own dead-stripping already recovers.

**Cross-compilation to Windows and Linux is now real and working (superseding the 2026-08-24 "per-OS native builds only" call below), confirmed 2026-08-27.** The two blockers that made the original call correct at the time are both actually fixed, not routed around: (1) `src/cli/main.zig`'s/`src/main.zig`'s own argv-parsing now goes through `std.process.Args.Iterator.initAllocator` (Zig's own portable argv parser) instead of `std.mem.span(argv[i])`, which never compiled for `x86_64-windows-gnu` (Windows' argv entry type differs from POSIX's `[*:0]u8`). (2) Extism's runtime being a host-OS-only prebuilt Rust binary turned out not to be a dead end -- Extism publishes real, official per-target prebuilt static libraries on its own GitHub releases (`libextism-<target-triple>-v1.30.0.tar.gz`), now fetched via `build.zig.zon` (5 targets: aarch64/x86_64 macOS, x86_64/aarch64 linux-gnu, x86_64 windows-gnu) and linked via `module.addObjectFile` (name-based `linkSystemLibrary` doesn't resolve a cross-target archive even with the right search path -- confirmed empirically). Windows additionally needs a real GCC-compatible unwind runtime (`llvm-mingw`'s `libunwind.a`, fetched the same way) since Extism's windows-gnu binary is GCC-mingw-built and Zig's own bundled windows-gnu support is LLVM-based; plus one tiny vendored stub (`vendor/mingw_compat/cfguard_dummy.c`) for a real, narrow gap in Zig's own bundled mingw-w64 CRT (`__guard_dispatch_icall_dummy`, a documented no-op even upstream). Linux needs no extra dependency at all -- `module.linkSystemLibrary("unwind", .{})` triggers Zig's own bundled real LLVM libunwind build, the same special-cased-library-name mechanism `-lc` uses for libc itself. Verified for real: `zig build test -j1` (native macOS, 78/78 steps, 661/661 tests) plus a full `natyv build` + app launch are unaffected; `x86_64-windows-gnu`, `x86_64-linux-gnu`, and `aarch64-linux-gnu` all now produce genuine, working executables (`file` confirms real PE32+/ELF) with zero manual build flags. **Linux (`aarch64-linux-gnu`) confirmed to actually *run* end-to-end, 2026-08-28** -- not just compile. Real VM test: Ubuntu Server 24.04.3 LTS ARM64 (minimized + bare Xorg, no desktop) in UTM (Apple Virtualization backend, native ARM64, no emulation), `natyv-core` with `examples/ntx-form` embedded, launched via `startx` + running the binary in the resulting bare `xterm`. Real window opened, real `natyv_dispatch ok` logs for hover/click/text_changed/blur, and the form's own logic worked end-to-end (typed a name, clicked Save, got "Saved: quinn"). Real VM test: Windows 11 ARM64 (25H2) in UTM -- note UTM's "Virtualize" option for a *Windows* guest actually runs under QEMU (with HVF acceleration), not Apple's native Virtualization.framework the way Linux got; real window (`ntx-form`) opened, real `natyv_dispatch`/`natyv_dispatch ok` logs, and the form's own logic worked end-to-end (typed a name, clicked Save, got "Saved: quinn"), plus a clean shutdown. Full detail: `~/.claude/plans/lexical-wishing-penguin.md`.

**Every per-platform or cross-compile-only dependency in `build.zig.zon` must carry `.lazy = true` -- shipped 2026-09-23 for the five `extism_*` entries and `llvm_mingw`, in both this repo and natyv-io/cli.** `build.zig` already guards all six behind `lazyDependency` (`resolveExtism`'s `orelse return null`, and `llvm_mingw`'s `if (...) |dep|` inside a windows-only branch), but the manifest never declared them lazy, so Zig fetched **all of them eagerly before `build.zig` ever ran**. Measured against an empty global cache: **378MB downloaded to produce a 52MB install, none of it used** -- all five Extism platform builds plus a 206MB llvm-mingw toolchain, on every clean build, whatever the target. Worst in `natyv-io/cli`, which is what Homebrew actually compiles: `natyv.rb` vendors Extism itself and passes `-Dextism-prefix`, so `resolveExtism` returns before it ever reaches `lazyDependency` and literally none of the 378MB could be used. After the fix, verified on a near-empty cache: the Homebrew path fetches **zero** tarballs, a normal native build fetches **exactly one** (`extism_aarch64_macos`, 31MB). **`sdl`, `mbedtls` and `shared` stay eager** -- those are unconditional `b.dependency` calls and genuinely always needed; marking them lazy would break the build. **When adding any new dependency here, ask whether every build actually needs it: if it is target-conditional, it needs both a `lazyDependency` call site and the `.lazy = true` flag, or it silently costs every user a download they never use.**

**Multi-OS distribution strategy, confirmed 2026-08-24 (see note above -- the cross-compilation blocker this was reacting to is now fixed, but the distribution-strategy question itself is still open pending real VM verification): per-OS native builds, not one-machine cross-compilation.** `natyv build`/`natyv prepare` are scoped to build for whatever OS they're invoked on; shipping to multiple OSes means running the same command natively on/for each target OS (e.g. via a future CI matrix), the same approach most real desktop apps use (Tauri, Electron-builder, etc.).

**`std.Io.net`'s `ConnectOptions.timeout` panics on the POSIX `Io.Threaded` backend, confirmed via a real spike 2026-08-30 -- never pass a non-`.none` timeout into an `IpAddress`/`HostName` connect call.** Scoping the planned TCP/TLS host function (raw sockets for the mail-client benchmark demo, see the network capability note above), a real standalone `zig run` program confirmed `Io.net.HostName.connect`'s own `imap.gmail.com:993` resolution+connect genuinely works (28ms, real DNS via std's own from-scratch `/etc/resolv.conf`-based resolver, no libc `getaddrinfo` delegation on this path) and already races connects across every resolved address concurrently for free (`connectMany`'s internal `Io.Queue` pattern -- real Happy-Eyeballs-equivalent behavior, no need to build our own). But passing any real `Io.Timeout` via `ConnectOptions.timeout` hits a bare `@panic("TODO implement netConnectIpPosix with timeout")` in `Io/Threaded.zig` -- a hard process crash, not a catchable error. **The verified workaround**: race the real connect against a separate sleep task via a shared `Io.Queue` (spawn both as `io.async` tasks, both push their result to the queue, take whichever arrives first via `queue.getOne`, cancel the loser with `future.cancel`) -- mirrors the exact pattern `HostName.connectMany` already uses internally, just one level up. Verified for real: a successful connect through this race returns as fast as the underlying connect does (26ms, not held hostage for the full timeout -- an earlier buggy version of the spike that just slept the full duration before checking got this wrong), and a deliberately unreachable test address (`192.0.2.1`, RFC 5737) was cleanly bounded to the intended timeout with no crash or leak. Any future natyv-core code that connects out over the network on this Zig version must use this manual race, never the built-in timeout field. **A second, narrower real finding the same day, after two rounds of correcting an over-broad conclusion**: `Stream.reader()`'s buffered `Io.Reader` wrapper, when reused across multiple reads on the same connection after a large prior read, sometimes fails to notice new data promptly (confirmed via absolute timestamps: a follow-up read occasionally didn't return until the *peer's own next action*, not when the data actually arrived) -- reproduced 100% of the time at exactly 1MB, probabilistically at other sizes. Root-caused to `Io/Reader.zig`'s `writableVectorPosix` (backing `Stream.Reader`'s own `readVec` override): when the reader's internal scratch buffer still has *some* unconsumed data (`seek != end`), it constructs the next raw read request purely against that buffer's own leftover capacity, which degenerates badly if that buffer happens to be exactly full but not fully drained. **The real fix (confirmed via a real test, 5 runs × 6 sizes = 30/30 clean, including the previously-100%-reproducing 1MB case): construct the reader with a zero-length buffer -- `stream.reader(io, &[_]u8{})` -- instead of a real scratch buffer.** With no internal buffer capacity, `seek == end` is permanently true, so the buggy branch is structurally unreachable and every read goes straight from the raw syscall into the caller's own destination. This is not a workaround; it's the library's own documented `readVec` contract ("implementations may ignore `data`, writing directly to `Reader.buffer`... or the reverse -- encouraged to take advantage of whichever simplifies the logic"), just configured to skip the optimization that has the edge case. **Confirmed design for the planned TCP/TLS host function**: use the real, unmodified `std.Io.net.Stream.Reader`/`Writer` types throughout (zero-length reader buffer, `HostName.connect` + the manual queue-race timeout workaround for connect) -- no custom vtable, no libc `recv`/`send` bypass, no platform-conditional shim needed anywhere; an earlier version of this note recommending a raw-libc-recv/send hybrid is superseded by this simpler, better fix. Full detail: `natyv-tcp-tls-host-function` memory.

**The `-j1` test workaround is retired as of 2026-09-23 -- plain `zig build test` is fine again.** The original note here (2026-08-24) said the default parallel runner "hangs/reports a spurious failure on one test binary when run concurrently with others," that isolating that binary (`zig test src/EventQueue.zig`) and running it alone passed instantly, and that `-j1` was a free workaround. **The real cause was found and fixed**: `EventQueue.push` printed to stderr on every push and coalesce, and Zig's build runner echoes any step producing *any* stderr as `failed command: <cmd>` -- with no `error:` line and **no effect on the exit code** (`compiler/build_runner.zig`'s "No matter the result, we want to display error/warning messages" block, gated on `result_stderr.len > 0`). Interleaved with parallel output it also corrupted the `--summary` tree's rendering, which is what made it look like a hang. Nothing was ever failing. Those traces are now gated behind `builtin.is_test` (see `src/EventQueue.zig`), and plain parallel `zig build test` passes **15/15 consecutive runs** in 2-3s. `-j1` still works and is harmless if you prefer deterministic ordering. **General lesson worth keeping: check a command's exit code; don't grep its output for words that look like failure.** Build tools print "error", "failed" and "warning" in passing contexts routinely -- this note existed for a month because of one such string.

## Core architecture (settled, built)

- **Host-runtime model**: natyv is the executable; the guest is a WASM plugin loaded into it — not an embeddable library devs link against. Chosen specifically because the widget vision (windows, file explorers) requires natyv to own the native UI layer itself.
- **Event contract**: one fixed `natyv_dispatch(event_bytes) -> response_bytes` guest export, not per-widget/per-event export names. "Registering a callback" is purely a guest-SDK-side concern (an in-guest id→handler table) — the host never knows about individual handlers, only "dispatch this event, guest figures out who cares." Avoids export-name collisions and supports dynamic handler registration.
- **Threading**: SDL owns the main thread (hard macOS/Cocoa requirement — window ops must be main-thread). A dedicated worker thread owns the Extism `Plugin` and makes all `natyv_dispatch` calls. Thread-safe queues move `{widget_id, event_type, payload}` one way and results back, drained once per frame on the main thread. Only one call into a given `Plugin` is ever safe at a time regardless, so this costs nothing extra.
  - A runaway guest handler can be cancelled via Wasmtime epoch interruption (`Plugin.cancelHandle()`). Verified against Extism's real Rust source: `store_needs_reset` is set only when the just-called export was literally named `_start`, unconditionally of cancellation — so the same `Plugin`/store is safe to reuse immediately after a timeout-cancel, no reinit needed.
  - `WidgetHost`'s registry (read/written by both threads) is protected by an `Io.Mutex`. Host-function callbacks are raw `callconv(.c)` and can't carry a Zig `Io` value across the C ABI — `Runtime.call(io, ...)` stashes `io` into `widgets.current_io` immediately before `extism_plugin_call` and unstashes after. Safe *only* because exactly one plugin call is ever in flight at a time and every host function invoked during it runs synchronously nested on the same thread — a genuinely non-obvious invariant, documented in `WidgetHost.zig`'s own file doc comment.

- **Main loop is real-event-driven, not busy-spinning — fixed 2026-09-03, `core@410d229`.** A live benchmark against Electron/Tauri found natyv-core sustaining ~70-93% CPU fully idle (both alternatives settle to 0%) — `main.zig`'s `while (running)` loop used non-blocking `SDL_PollEvent` with no `SDL_Delay`/`SDL_WaitEvent`/vsync at all, and `FrameLoop.drawWindow` redrew unconditionally every iteration regardless of whether anything changed. Fixed with `SDL_SetRenderVSync` (`WindowManager.createWindowContext`) + `SDL_WaitEventTimeout(16ms)` replacing the unthrottled poll, plus a real draw-level dirty check in `drawWindow` gated on `WidgetHost.layout_generation` changing (**not generation alone** — `Spinner`'s animation and `Button`'s click-flash are both timer-driven with no generation bump at all, confirmed via their own doc comments, and are explicit exceptions to the gate) OR an active slider drag OR the 500ms per-window warmup (`WindowContext.created_at_ms` — a freshly-created window's first `SDL_RenderPresent` isn't reliably guaranteed to display by the OS compositor, a real bug found via the very first live click-through after the dirty check landed). `Dispatch.run` pushes a registered `SDL_RegisterEvents` event after every `natyv_dispatch` call so a worker-thread-driven widget mutation wakes the main loop immediately rather than waiting out the timeout. Real result: idle CPU ~70-93% → ~8-16%, idle RSS unchanged.
  - **A real, separate gap in the draw-level dirty check itself, found 2026-09-06 via the memory-reclamation spike's own live click-through (unrelated to recycling — recycling's async timing just made it far more likely to actually get hit): `needs_continuous_redraw` only ever reports whether a Button flash/Spinner animation is *still* active, never whether one just *ended*.** The exact frame that transition happens reports `false`, identical to an ordinary idle frame — if nothing else also changes that same frame, the redraw is skipped *and* `needs_frequent_wake` goes false in the same instant, permanently freezing the widget on its last mid-animation frame with nothing left to force another look. Confirmed via two `sample <pid>` stack captures during a reported freeze (both showed the main thread cleanly parked in `SDL_WaitEvent`, every other thread idle — ruling out a deadlock and pointing straight at this gate, not a concurrency bug). Fixed generically: new `WindowManager.WindowContext.was_continuous_redraw` tracks the previous frame's value; `FrameLoop.drawWindow` now also redraws on the falling edge (`was_continuous_redraw and !needs_continuous_redraw`).
  - **A pre-existing architectural characteristic became a real, visible bug once the loop stopped being unthrottled**: `main.zig`'s per-frame widget snapshot, Clay layout pass (`layoutWindow`), and TTF_Text sync (`syncTextObjects`) were all computed exactly once per iteration, *before* that same iteration's own input events were processed — always true, invisible under the old busy-spin loop (the next iteration, microseconds later, already had fresh data), but a real one-event lag once the loop only wakes on real events. Fixed by calling all three again, right after the event-draining loop, before drawing (`FrameLoop.rebuildFrameSnapshot`/`FrameLoop.syncAllWindowText` are new shared functions extracted for this; `layoutWindow` is called a second time directly). Any future change to this loop's own timing must re-verify text input, Refresh/pagination-style re-renders, and newly-created-widget positioning live, not just via `zig build test` — none of these three bugs were caught by the existing test suite. Full detail: `project_natyv_render_loop_fix` memory.
  - **A third real bug in this same lineage, found 2026-09-07 via the memory-reclamation ergonomics layer's mail-natyv retrofit (unrelated to that retrofit's own guest-side code — a pre-existing host bug the retrofit's heavier click-through was the first to trigger): `FrameLoop.drawWindow`'s own `current_generation` used to read `widgets.currentGeneration(io)` fresh and independently, instead of the generation value the *actually-computed* Clay geometry reflects (`ClayLayout.last_computed_generation`, updated only when `layoutIfNeeded` runs a real recompute).** `WidgetHost.layout_generation` is bumped *outside* the slot mutex, and the main thread's `layoutWindow`/`drawWindow` calls aren't synchronized to "one complete guest dispatch's worth of mutations" — so a single dispatch doing several sequential widget-tree mutations (e.g. `Destroy()` a multi-widget view, then `SetVisible(true)` a different persisted one) could have `layoutIfNeeded` capture an *intermediate* generation mid-sequence and compute geometry against it, while `drawWindow`'s own *later*, independent read already saw the *final* value — crediting `wctx.last_drawn_generation` with a generation whose geometry was never actually drawn. The next frame's real, correct recompute then silently never gets drawn, since the generation comparison already (wrongly) shows no change — permanently, until an unrelated later event bumps the counter again. Symptom looked exactly like a stuck/frozen redraw with no error anywhere; confirmed via temporary `std.debug.print` instrumentation in `setVisible`/`layoutIfNeeded`/`drawWindow`, not by inspection alone. Fixed by having `drawWindow` read `wctx.clay_layout.?.last_computed_generation` instead of an independent counter read (falling back to the old direct read only when there's no Clay layout for the window, or it's never run a real pass yet) — makes this bookkeeping structurally unable to diverge from what was actually drawn. Full detail: `project_natyv_render_loop_fix` memory.
  - **A real, currently-OPEN bug class found 2026-09-09, confirmed recycle-adjacent, NOT a styling/rendering-technique issue**: after a `Runtime.recycle()` has happened at any point in an app's lifetime, some later-drawn visual state never becomes visible on screen even though it's provably computed and issued correctly — confirmed two ways. (1) A Button's real 150ms click-flash fails specifically on any click immediately followed by a recycle (4/4 in one real click-by-click test), never on a click with no adjacent recycle. (2) mail-natyv's row/toolbar `ApplyStyle`d backgrounds intermittently render as if never styled at all, structurally present (text/checkboxes fine) but visually flat against the parent. Hypothesis (2) was originally attributed to `CreateContainer`/`ApplyStyle` being separate, independently-locked host calls (a real gap — see the atomic-create+style mechanism below) — that mechanism was built (`ClayLayoutRequest` gained optional style fields, applied under the same lock as insertion; Go SDK gained `ApplyStyleToLayout`) and confirmed via instrumentation to close the race for real, but live-testing it against the actual bug showed **no change — still reproduces**. Direct instrumentation logging `background_color`/`corner_radius`/rect/clip at the exact draw call, across a full real recycle+rebuild sequence, showed **100% correct data on every single drawn row** — the bug is not in the widget/style data reaching the draw call at all. Two independent experiments swapping `ShapeCache`'s entire draw mechanism (cache-bypass; then a full bypass drawing tessellated geometry directly to the real target with zero offscreen texture/render-target-switching/caching) both left the bug completely unchanged — the rendering *technique* is not implicated either, closing out a reasonable but ultimately wrong parallel to the old SDF-shader bug that motivated the current technique (see this file's own Styling system section). **The one variable that matters, confirmed via a clean A/B**: with `recycle_threshold_mb` set high enough that no recycle ever fires, the exact same repeated page-navigation sequence never reproduces the bug, across many tries. With recycling on, it reproduces on rebuilds well after the recycle itself completed, not just the one frame immediately following it. - **Memory-reclamation recycle mechanism, real and shipped (2026-09-06).** `Runtime.zig`'s `loadPlugin` now goes through `extism_compiled_plugin_new` (once, stored in a new `compiled` field) + `extism_plugin_new_from_compiled` (cheap, no re-JIT) instead of a single `extism_plugin_new` — this is what makes a later recycle fast (~30ms measured in the Phase 1 spike). A new `Runtime.recycle(io)` method: calls the guest's optional `natyv_checkpoint() -> bytes` export on the live instance (dupes the returned bytes into host-owned memory immediately — the first place a call's output must survive another `extism_plugin_call`/`extism_plugin_free`, an easy FFI lifetime bug), builds a fresh instance from the same compiled artifact, calls `natyv_resume(bytes)` on it, and only on success frees the old instance and swaps the pointer — never destroy-then-create, so a failure at any step just keeps the old instance running. `can_recycle` (both exports present, checked via `extism_plugin_function_exists`) gates this to a no-op for any app implementing neither. `Dispatch.zig` triggers it between dispatches (the same single-call-in-flight window every nested host-function call already relies on). **The widget registry itself needs zero changes for this to work** — `WidgetHost` lives entirely host-side, untouched by which guest plugin instance is calling into it. **What does NOT survive automatically, confirmed the hard way (2026-09-06 real click-through): guest-side event handler registrations.** `OnClick`/`OnChange`/etc. (`sdks/go/widgets/internal/dispatch.go`'s handler maps) are pure in-guest state populated only by `natyv_init`, which never runs on a resumed instance — `natyvDispatchExport`'s own router treats a missing handler as a silent no-op success, not an error, so a real click after a recycle looks identical to a successful one in the host's own logs while doing nothing at all. Any hand-written (or future auto-generated) `natyv_resume` must explicitly re-register every handler the app cares about, the same way it must reattach to existing widget ids via a `WrapX`-style SDK helper (`widgets.WrapLabel` is the first of these, added alongside this work) — restoring data alone is not enough. Full detail, including two other real bugs found the same way (a `Dispatch.zig` wake-event ordering bug, and the redraw-gate falling-edge fix noted above): `project_natyv_instance_recycling_idea` memory.
- **Real recycle trigger, replacing the fixed-dispatch-count stand-in (2026-09-06, live-verified).** New `src/process_memory.zig`: `residentSetSizeBytes(io) !u64` returns real OS process RSS via a `switch (builtin.os.tag)` — comptime-known, so this costs nothing at runtime and the non-matching platforms' bodies are never analyzed for whichever target is actually being compiled (same idiom `std/c.zig` itself uses for `getrusage`/`rusage`). macOS uses already-in-std `std.c.task_info`/`mach_task_self`; Full detail: `project_natyv_instance_recycling_idea` memory.
- **Host-owned persisted state (`natyv.Persisted[T]`), real, built, and empirically verified end to end (2026-09-09).** The ergonomics-layer replacement for hand-written `natyv_checkpoint`/`natyv_resume` state-tracking: app data lives host-side from the moment it's written, via a plain generic Go SDK function, rather than trapped in guest linear memory the recycle mechanism above can't shrink. `core/src/PersistStore.zig` (new, lives directly in `src/`, not `capabilities/` — deliberately dependency-free so it gets its own clean test root; Full design history: `project_natyv_ergonomics_layer` memory; plan: `~/.claude/plans/lexical-wishing-penguin.md`.
- **Guest-facing logging, real and built (2026-09-03).** Needs zero new host functions — Extism's own `extism:host/env log_*` imports are already available to every plugin for free (`sdk/go`'s `LogInfo`/`LogWarn`/etc. wrap `pdk.Log` directly). `conf.natyv.json`'s `logging` field (`null` disables entirely; `"stdout"`/`"stderr"`; anything else is a filename resolved via `SDL_GetPrefPath`, same convention `sqlite.filename` already uses) controls the *destination* only — level filtering is deliberately not config-driven; `src/Logging.zig` always subscribes Extism at its most permissive level (`extism_log_custom("trace")`) and lets the drain handler (or, today, nothing) decide what to do per level, since which level a call logs at is entirely a guest-code decision. A real file destination uses manually-tracked positional writes (`file.stat(io).size` at open, `writePositionalAll` per line) rather than relying on any OS-level append-mode open flag, since this Zig version's `std.Io.Dir.CreateFileOptions` has none — confirmed correct across separate process launches (the file grows and old content survives a fresh launch, not overwritten). Real, live end-to-end proof: a real guest `LogInfo` call in `mail-natyv` was traced all the way through to both a real stdout capture and a real on-disk file (confirmed via `SDL_GetPrefPath`'s actual resolved location), including confirming append-across-launches by running twice and seeing the line appear once per run in a growing file.

## Widget system

- `WidgetHost.slots`: **heap-backed and growable since 2026-09-07** (`std.ArrayListUnmanaged(?Slot)`, was a fixed `[max_widgets]?Slot` array before) — `insertLockedWithLayout` scans existing (destroyed-and-freed) slots first, same as always, and only appends (growing the registry by one) when none is free; a real allocation failure degrades to the same `error.RegistryFull`/"widget registry full" guest-facing contract as before, unchanged. Converted specifically because `WidgetHost` is embedded *by value* inside `Runtime` (itself a stack-local in `main.zig`, and returned by value from `Runtime.init`) — a fixed array here meant `Runtime`'s own size (and every other place embedding either by value) scaled directly with `max_widgets`, and bumping that constant (see below) produced a real, live-reproduced cascade of stack-overflow segfaults before this fix. `pending_text_destroys` got the same treatment (also heap-backed, reused via `clearRetainingCapacity` each frame). `max_widgets` itself is unchanged as a named constant (now 2048, up from 192 -- see its own doc comment for the real mail-natyv capacity arithmetic that forced the bump) but is **no longer a hard ceiling on `slots`** — it's still used to size `main.zig`/`FrameLoop.zig`/`ClayLayout.zig`'s own per-frame render-loop scratch buffers and `DrawBatcher.zig`'s per-color rect buffer, all still stack-allocated or struct-embedded and therefore still capable of reproducing the same class of stack-overflow bug if bumped again without checking — a full dynamic-growth conversion for those too is scoped but not started (see `project_natyv_ergonomics_layer` memory, "the redesign direction" section, 2026-09-07). `SnapshotIndex`'s own capacity (now 8192, was 512) is separately bounded and its probe loop is now hang-proof (bounded to `capacity` probes, degrading to "not indexed" on a genuine overflow rather than looping forever) regardless of `max_widgets`'s value. `next_id` is monotonic, never reused. `layout_generation` is one global dirty counter, not per-surface (accepted v1 inefficiency for multi-window: an edit in window A forces window B's independent `ClayLayout` to also recompute that frame — correct, just not maximally efficient).
- **`natyv_destroy_children_except` (2026-09-07)**: a second rebuildable-region primitive alongside `natyv_destroy_children` — destroys every current child of a widget except one named child's entire subtree, which survives untouched. `WidgetHost.destroyWidgetChildrenExcept`/`destroyDescendantsExceptLocked` (host), `widgets.Container.DestroyChildrenExcept` (Go SDK). Built for a make-before-break region-swap design (build a replacement subtree as a hidden sibling first, reveal it, only then destroy the old one — avoids the visible "destroy first, then rebuild" flash a naive swap produces whenever the rebuild does anything slow) — the mechanism itself is real, host-level infrastructure independent of whether that specific region-scoping approach survives; see `project_natyv_ergonomics_layer` memory for the full design and its current (paused, under reconsideration) status.
- **`Manifest.timeout_ms` (2026-09-07): bumped 8000 -> 20000.** A hard per-dispatch deadline Extism's own Wasmtime runtime enforces internally — exceeding it doesn't return a clean error, it forcibly terminates the WASM call mid-execution, which can leave a guest instance's own state inconsistent (real, live-reproduced: a retry-with-reconnect pattern doing two full network round trips in one dispatch exceeded the old 8s budget under real network slowness, got killed mid-flight, and left the guest visibly broken until relaunched). Any guest code that retries a slow operation (network, disk, anything) needs to fit within this budget, whatever it's currently set to — there's no per-call override today, it's one fixed value for every dispatch.
- **`DrawBatcher.max_colors` (2026-09-07): bumped 8 -> 32.** Sized against a simple test fixture's own "four colors" baseline; a real, styled app's stylesheet can easily need more distinct fill colors in one frame than that. `DrawBatcher.add` silently drops a rect if the color-bucket cap is exceeded (by design, matching the widget registry's own old "silently cap out" posture) — exceeding this doesn't crash or error, it just silently stops drawing some widgets' backgrounds that frame. Revisit if a future app's own stylesheet approaches 32 distinct background/fill colors in one screen.
- Every widget struct uses fixed-size buffers (e.g. `Label`'s 256-byte text buffer) — this is a deliberate, load-bearing discipline, not incidental: natyv's entire widget registry costs ~32KB at its hard cap, against a measured ~45MB idle baseline (Wasmtime/Cranelift dominates; widget count/kind is noise). Keep this bounded-by-construction pattern intentional as new widgets/capabilities land — don't let memory footprint creep the way Electron's does.
- **Widget creation is NOT a meaningful startup cost — measured 2026-09-23, correcting an earlier note here that claimed ~6ms per widget.** Direct per-phase instrumentation (enable with `NATYV_STARTUP_TRACE=1`, see `src/timing.zig`) puts a real app's whole startup at **~115-135ms to first window**: `SDL_Init` ~65-76ms (~60% of it), JIT compile 13-22ms, guest instantiation + TinyGo `_initialize` ~2-3ms, and `natyv_init` only **2-6ms** for an app that does no network. Per-widget creation is **~0.14ms** including the host-side registry insert (27 extra create sites between two real fixtures cost 3.9ms); an isolated spike put the bare JSON round trip at ~20µs. Batching every create into one host call was measured to save **0.25ms** — it is not worth building, and neither is a binary encoding. If an app launches slowly, the cost is almost certainly in what its own `natyv_init` does (mail-natyv's is 4409ms, essentially all `connectIMAP()`), not in widget creation. Full record and the two proxy-measurement mistakes that produced the wrong number: `project_natyv_startup_measurement` memory.
- **`WidgetHost.findLocked(id)` is now O(1), done and verified 2026-08-24.** New `id_to_index: std.AutoHashMapUnmanaged(u32, usize)` field, kept in sync at every real site a slot is ever assigned or freed -- `findLocked` itself just does `self.id_to_index.get(id)` then indexes into `slots`, replacing the old O(`max_widgets`) linear scan. `.empty` (Zig's unmanaged-hashmap zero-init, matching this codebase's own already-established `ArrayList`-unmanaged convention) rather than `.init(allocator)`, since `WidgetHost` has no explicit init/deinit lifecycle today -- every real construction site is still a plain struct literal. Added a real `WidgetHost.deinit()` (frees just the map -- `slots` is a fixed-size array, nothing to free there) and wired it into `Runtime.deinit()`, which previously had nothing to do for `widgets` at all. **`findLocked`'s own signature never changed**, so none of its ~35 real call sites across `WidgetHost.zig`/`WidgetHostFunctions.zig`/`RuntimeTest.zig` needed touching -- a pure internal optimization.

- **`natyv_destroy_widget` cascades to descendants, done 2026-09-01** — supersedes the note two bullets above describing it as "intentionally separate" from `destroySubtreeLocked`'s cascading behavior; that separation was never a deliberate safety choice, just something nobody had generalized to the plain guest-facing destroy call yet. ## Host-function security invariants (audited 2026-09-24/25, all findings fixed 2026-09-25)

**`WidgetHost.max_widgets` (2048) is the hard cap on `slots`** — enforced in `insertLockedWithLayout`
(returns null → `error.RegistryFull`). Every `[max_widgets]` scratch buffer relies on it, and each write
also checks `.len` as a second line of defence (fixed 2026-09-25; before that a guest could force an
OOB stack write in ReleaseSmall).
- **Do not add another `[max_widgets]` buffer** without bounds-checking the write.
- `DrawBatcher.zig:61` is the correct pattern (`if (self.counts[i] < max_widgets)`).

**Guest SQL may not name files.** `Sqlite.open` installs an authorizer: `ATTACH` only with an empty
filename (plain `VACUUM` attaches `''` internally — a blanket deny breaks it), `DETACH` and the
`temp_store_directory`/`data_store_directory` pragmas denied. This blocks `ATTACH '<path>'` and
`VACUUM INTO '<path>'`, which read/write anywhere at host privilege. Everything inside the host-opened
database stays allowed. Widen only on real need, and host-mediated (guest names, host picks paths).

**Persisted state is capped** (`PersistStore.max_entries` 4096, `max_total_bytes` 16 MiB, counting both
the value store and the freed-keys set). It lives outside the guest's wasm memory and survives recycling,
so it must never grow unbounded; past the cap the host fn returns `persist limit reached`.

**Truncate text with `text_cursor.truncatedLen(s, max)`, never `@min(s.len, max)`** — a byte cut can
split a multi-byte sequence and hand SDL/SDL_ttf invalid UTF-8. Every fixed-buffer text copy uses it.

**Guest numbers are validated at the wire, and every use site is safe on its own anyway.** Out-of-range
`@intFromFloat`, integer overflow, `@mod` by ≤ 0 and `std.math.clamp` with `lo > hi` are a Debug panic
and silent UB in ReleaseSmall (what ships). `std.json` parses `1e999` as `inf`, so:
- `WidgetHostFunctions.parseRequest` rejects any request containing a non-finite float (`allFinite`).
  Every widget host fn must parse through it.
- Every float→int on a guest-reachable value uses `std.math.lossyCast` (saturates, NaN→0), never
  `@intFromFloat` — rects, sizes, clip rects, colors, SDL window dims, `ShapeCache` mask dims
  (`maskInt`, also capped so `dim * aa_level` fits a texture).
- Integer arithmetic on guest values uses saturating ops (`+|`, `-|`), or widens to `i64` first
  (`NumericStepper.resolve`'s wrap).
- `clamp(x, lo, hi)`/`@mod` only where the bounds are known valid: normalize guest pairs first
  (`NumericStepper.init` orders min/max, `RangeSlider.setRange` clamps the upper bound before using it).

**Windows are capped at `WidgetHost.max_window_roots`** (`WindowManager.max_open_windows - 1`; the
startup window takes the other). `main.zig` silently drops window requests past its own cap, so
`insertWindowRoot` refuses first rather than hand the guest an id with no window behind it. Destroy a
window only through `WidgetHost.destroyWindow` (both `natyv_destroy_window` and `natyv_destroy_widget`
do): it cancels a still-pending create request instead of queueing a teardown, because `main.zig`
drains teardowns before requests and would otherwise create an OS window for a dead widget.

**`zig build test` never compiles host-fn callbacks or `FrameLoop.zig`** — Zig only analyzes what a
test references, and nothing references the `capabilities/*.zig` callbacks or the `main.zig`-only
`FrameLoop`. Run `zig build` too after touching them (a type error in `Persist.zig` passed all tests).
The same goes for `test` blocks: a file's tests only run if a test root reaches the file.
`WidgetHost.zig` pulls in `WidgetHostFunctions.zig`'s with `test { _ = HostFunctions; }`, and
`RuntimeTest.zig` is not in the test step at all. Break a new test on purpose once to prove it runs.

**Rule going forward: any host function that exposes a resource must bound it and reject past the
bound.** `Tcp.zig` and `TrayRegistry.zig` are the reference implementations (`orelse return Error`,
validated ids, clamped sizes). Full findings in the `natyv-host-function-audit` memory.

## Project structure conventions

Modeled directly on real patterns from Zig's own stdlib and the Extism Zig SDK, not ad hoc:
- **File-as-struct idiom** for single-type modules (PascalCase filename, `const Self = @This();`, no wrapping `pub const X = struct {}` block) — e.g. `EventQueue.zig`, `WindowManager.zig`.
- **One shared `c.zig`** as the single `@cImport` boundary every other file imports through — required, not just tidy: two independent `@cImport` blocks with identical content still produce distinct incompatible types in Zig.
- **snake_case files for grouped utility functions/constants** (`timing.zig`, `json_util.zig`), matching std's own `time.zig`/`fmt.zig` convention — PascalCase = single type, snake_case = grouped functions.
- **Embedded assets under `src/assets/`, not a sibling top-level directory** — actually required, not conventional: Zig 0.16's `@embedFile` rejects paths escaping the module's root directory.
- Split files by real seams, not line count alone, once they grow large (already done once: `Runtime.zig`/`WidgetHost.zig` split for length).

## Multi-window architecture

Full design/rationale: see the plan `~/.claude/plans/lexical-wishing-penguin.md` (all 5 stages shipped, see README). Key durable facts:
- A window root is a `ClayStyle.window_root` marker flag on a plain `Container` slot, **not** a new `WidgetKind** — confirmed via a full exhaustive-switch audit; zero `Widget`-union switches need touching for this.
- Real OS resources (`SDL_Window`/`SDL_Renderer`/an owned `ClayLayout`/a per-window `TTF_TextEngine`) live in `WindowManager.WindowContext`, owned by `main.zig`/`FrameLoop.zig`, outside `WidgetHost` — SDL/Clay/TTF creation is main-thread-only. `TTF_TextEngine` is genuinely renderer-specific (confirmed against `TTF_CreateRendererTextEngine`'s own precedent), so it multiplies per window; `default_font` itself stays one global.
- `FloatingOrder.windowSubset`/`nearestWindowRoot` partition a widget snapshot to one window's own subtree — needed because every hit-test/hover/draw/layout pass is otherwise unpartitioned across the whole flat registry.
- **SDL_ttf cross-thread destruction order is a real, easy-to-violate invariant**: every `TTF_Text` must be destroyed (main-thread only) before its owning `TTF_TextEngine` is destroyed. Two real crashes were caused by violating this (destroying text directly from the worker thread; destroying a window's text engine before its own queued text objects were flushed) — always route text destruction through `queueWidgetTextDestroysLocked`, and always flush pending text destroys at the very top of the frame loop, before any window-teardown draining.
- Window creation uses a real bounded FIFO queue (`pending_window_requests`/`pending_window_teardowns`, cap 8), not a single-slot precedent — a guest could request several windows in one dispatch call before the main thread drains anything.
- **`drawWindow`'s real layering order, bottom to top: ordinary content → floating-non-modal content → modal backdrop + modal content — and every scrollbar thumb must be drawn *within* its own layer, not as one unconditional pass at the end.** Found via a real click-through (2026-09-02, `.ntx`'s new `scroll:` NTSS property intersecting with the also-new `Dialog` widget): a scrollable ordinary Container's own scrollbar thumb visibly drew on top of an open modal, because the original code drew every scroll container's thumb in a single unconditional pass placed after *everything else*, including the modal backdrop and its own content. Fixed by extracting `drawScrollbarFor(slot, clay_layout, renderer)` and calling it three times, interleaved with the existing three widget-drawing phases (non-floating, floating-non-modal, modal-descendant) using the exact same `is_floating`/`topmost_modal`/`FloatingOrder.isDescendantOfOrSelf` filters those phases already use — not a new mechanism, just correcting an oversight in an already-correct layering model that the scrollbar-drawing code was never folded into. Any *future* per-frame overlay drawn outside the normal widget-fill/decoration path (a cursor, a drag-ghost, a debug overlay) needs the same three-phase treatment, not a single end-of-frame pass, or it will have this exact bug.

## Styling system

**Layout engine confirmed: staying on Clay until Yoga is explicitly needed (2026-08-24).** Yoga was researched and preferred on paper at one point (see `natyv_styling_system` memory), but integration cost wasn't worth it without a real, concrete need driving it -- Quinn's call closes this out as a non-decision for now, not a live open question. The styling system remains intentionally not engine-neutral.

**Rendering technique, shipped 2026-08-22: plain-SDL tessellation + render-to-texture caching (`src/capabilities/ShapeCache.zig`) — no custom GPU shader anywhere in v1.** Replaced the earlier `SDL_GPURenderState`/SDF-shader approach (Stage 1, fully deleted — `ShapeShader.zig`, `src/shaders/`) after an unresolved rendering bug (never root-caused — see `natyv_styling_system` memory for the full debugging trail) prompted a reconsideration of whether GPU shader dependency was ever the right call for something as basic as rounded corners. RadioButton draws a real circle/ring through it today; Checkbox needed no change at all (`SDL_RenderRect` was already a perfectly sharp square).

- **The technique**: tessellate the real shape (true circle/rounded-rect polygon, high segment count) at 4x the target size into an offscreen `SDL_TEXTUREACCESS_TARGET` texture, then blit it back down to the real size with `SDL_SCALEMODE_LINEAR` — the scaled-down blit's own filtering does the antialiasing. Cache the final, already-downsampled alpha-mask texture (not the supersampled intermediate), keyed by shape parameters, lazily on first draw. Reused every frame after that as a plain blit — no per-frame tessellation cost once cached.
- **Confirmed default: 4x supersampling** — chosen by live visual comparison (1x/2x/3x/4x/5x side by side on a circle, rounded rect, and diamond): 1x has visible stair-stepping on both round and diagonal edges, 2x already looks clean, 3x-5x are barely distinguishable from 2x at typical UI sizes. A future styling-system knob will let devs override the pass count explicitly; 4x is the built-in default.
- **Fill/gradient/texture, all shader-free**: flat color via `SDL_SetTextureColorMod`/`SDL_SetTextureAlphaMod` on the cached mask. Gradients don't need a shader either — `SDL_RenderGeometry`'s native per-vertex color interpolation *is* a linear gradient; render one into its own small texture and composite through the mask via a blend mode. Texture fill: same masking approach with the user's own image. Border: a second, smaller inset mask isolating the ring.
- **Why this is strictly better for v1, not just a workaround**: works identically on any SDL renderer including a pure software one — zero GPU-capability fallback story needed, since there's nothing GPU-specific in the critical path at all.
- **Token/API model** (unaffected by the rendering-technique swap): named-style-tokens, not a CSS cascade/selector engine. One unified API for layout + visual properties. Multi-token composition merges by declaration order (later overrides earlier on conflict — a plain field-merge, not CSS specificity). Resolution happens entirely guest-side; the host wire contract is unchanged (it always receives fully-resolved property values). A `natyv` bundle step parses the stylesheet once (one shared parser regardless of guest language) and generates a per-language source file of *already-resolved literals* (not an encoded blob), embedded via each language's own native mechanism.
- **Guest-authored custom rendering code is explicitly rejected**, not deferred — would push toolchain/trust-boundary burden onto every third-party natyv-app developer, a real departure from natyv's otherwise fully closed, host-validated guest vocabulary. A host-defined rendering path, parameterized through the existing wire contract, is the model instead.
- **Clay's transition/animation system is real and verified working** (not a declarative stub) — retained per-element state across frames (`context->transitionDatas`), a real state machine, real elapsed-time accumulation, a real built-in easing function. Two real natyv-side gaps, not yet fixed: `ClayLayout.zig` hardcodes `Clay_EndLayout(0.0)` at all 3 call sites despite already computing a real `delta_time_s` locally — must thread it through or transitions never advance. And the interpolated visual values only surface via `Clay_RenderCommandArray`, which natyv discards entirely today (`Clay_GetElementData` is geometry-only) — adopting transitions means consuming render commands for visual properties, real new work.
- **Text styling**: adopt Clay's *vocabulary/naming* for text config, but SDL_ttf stays the execution path — natyv does not and will not call `Clay__OpenTextElement`; this is a naming alignment, not a hand-off of text layout to Clay.

All bare numbers are pixels (matches Clay's real integer-pixel fields; unrelated to `CLAY_SIZING_PERCENT`, which is width/height only). Colors are authored as hex strings (`"#RRGGBB"`/`"#RRGGBBAA"`), compiled by `natyv prepare` into `SDL_FColor` — same pipeline for flat colors and both gradient stops. Gradient position uses 8-direction anchors (top/bottom/left/right/corners), deliberately simpler than CSS's angle-based gradients. `text` and `transition` both live inside the token (not separate JSX attributes) — consistent with the one-unified-API token model.
- **`texture` requires image capability opt-in via `conf.natyv.json`** (same posture as sqlite/network) — if referenced without that capability enabled, `natyv prepare` must eventually emit a real warning/error, never silently drop it. **Interim state, confirmed 2026-08-21**: that flag doesn't exist yet (needs asset staging first), so `Codegen.zig` silently drops `texture` from its output today rather than stubbing a check against a flag that isn't real — revisit once asset staging lands.
- **Asset embedding phase split**: `natyv prepare` only stages files (copies the app dev's own `/assets` into natyv's own `/assets` location) — no compiler involved. `natyv build` is the only phase that invokes the real Zig compile (`zig build`) doing the actual `@embedFile`-driven embedding into the final binary. Zig's `@embedFile` is already real, working precedent in this repo (`src/assets/`).

## JSX-like markup authoring layer

**Confirmed design, not yet researched into a staged build plan** (full detail: `natyv_jsx_markup_layer` memory; suggested next step is a minimal virtual-doc/source-map spike before full architecture commitment).

- Tags are natyv's own widget type names directly (`<Button>`, `<Container>`, `<TextField>`) — **not** HTML tag names. This is deliberate: literal HTML-tag mapping invites false "so I can paste my HTML" expectations and an ongoing per-tag mapping tax; direct widget-name tags have neither problem, since the tag vocabulary *is* the widget vocabulary by construction (same move React Native made with `<View>`/`<Text>`).
- **Compile-time transpiler only, never a runtime interpreter** — same zero-new-runtime-cost shape as everything else here.
- **File-splitting, not merging**: a single authored file (illustrative extension `.go.ntx`, `.rs.ntx` — compound extension is load-bearing: stripping `.ntx` leaves the real target-language extension, self-describing per file, and creates zero collision with a real compiler's own source globbing since e.g. `save_form.go.ntx` doesn't end in `.go`) gets "unwound" into two fully separate, independently-valid real source files — a generated file with the actual widget-construction calls, and the developer's real logic left almost untouched with the JSX block replaced by a call into the generated builder. Both land in the same package/module; the host language's own compiler links them with zero natyv-side merging logic. This is deliberately *not* Vue SFC's approach (compile-and-splice into one synthesized file) — it avoids natyv's transpiler needing to understand enough of the target grammar to merge two syntaxes.
- **Composer discovery: `expose <Name>` header block, not inline-JSX-anywhere-in-expression-position** (confirmed 2026-08-24, corrects an earlier framing that implied disambiguating `<Tag` from the host language's own `<` at arbitrary expression positions — real JSX/TSX needs expression-context awareness this arc avoids, and a first-pass "uppercase letter after `<`" heuristic was Go-safe but explicitly unsafe for Rust's `<>` generics/turbofish). A file's first non-comment, non-blank line(s) must be one or more `expose <Name>` lines (multiplicity supported, deliberately placed at the very top so a file's public composer surface is readable without scrolling); each name is then located via a plain `func Name(...) {` text match later in the file, and that function's **entire body** (found via the same brace/string/comment-aware scanning already used for attribute values) is 100% markup grammar. Anything not named in an `expose` line is untouched host code. Generalizes cleanly to any guest language (a named function declaration is unambiguous everywhere; a bare `<` isn't). Naming is `expose`, not `export` — Go already gives "export" its own load-bearing meaning (capitalization).
- **`ref={&variable}` binds a widget declared inside its own tree for later reference by a handler** — a pre-declared variable, assigned once by the generated builder, closed over by handlers. Mirrors React's `ref`. Per-language mechanism varies: Go uses a plain pointer; Rust needs `RefCell` behind an immutable `static` (not `static mut`) to preserve the same "stable slot filled in later regardless of tree order" property under Rust's ownership rules; C's `&` is a natural, direct fit; Python has no address-of operator at all, so `ref={"name"}` string-name binding is the (unresolved, real gap) workaround, and both the builder and any handler touching it need explicit `global`.
- **Attribute values must be real per-language expressions**, not a universal natyv-invented mini-syntax (e.g. `styles={[]string{"x"}}` in Go, `styles={&["x"]}` in Rust, `styles={["x"]}` in Python where it happens to coincide) — this is load-bearing since `onClick={handleSave}` already requires real per-language identifier resolution; the transpiler needs a real expression-level parser per guest language, not just tag-syntax parsing.
- **One deliberate exception to the rule above: `styles={token_a, token_b}`** — a bare comma-separated style-token-name list, expanded by the transpiler into the language-native literal (`[]string{"token_a", "token_b"}` in Go, etc.), same special-cased category as `ref` since natyv already validates token names against the stylesheet at `prepare` time (a closed, parser-owned vocabulary, unlike `onClick`'s arbitrary guest symbols). Anything that doesn't parse as a bare identifier list (e.g. `styles={isActive ? "active" : "default"}`) falls through to a real host-language expression, passed through as-is — this is the dynamic-styling path. **The host function this calls (`natyv_set_style`, real and built — see this file's Styling system section) takes already-resolved literal values, never token names** — the host stays completely ignorant of "tokens," matching the token model's own "resolution happens entirely guest-side" principle below. The name→resolve→merge (later-wins cascade) step lives in a Go SDK helper (`ApplyStyle`) reading the generated `StyleTokens` map, not in the host. Otherwise cheap because Clay is from-scratch-every-frame, so a changed `Slot`-level resolved style is picked up automatically next frame with no new render mechanism. Static usage still fully bakes/merges at `prepare` time for zero runtime cost.
- **Rust has a real alternative architecture worth weighing if/when pursued**: Yew's `html!{}` proc macro already proves inline JSX-like syntax can be embedded natively via Rust's own macro system, no external file-splitting transpiler needed — a genuinely different, Rust-only mechanism from the external-transpiler approach used elsewhere.
- **Reusable component trees (React-style, colocated with the feature that uses them) mirror the guest language's own real package/module boundaries — natyv never invents its own package model. Real, built, Stage 6a below** (this bullet is the original design; see the Stage 6a bullet under "Composer discovery" below for what actually shipped, including the real `<children/>` mechanism this design left unspecified). A `.ntx` file's generated output lands in whatever package its directory already implies under that language's real rules, so cross-feature reuse is just a normal cross-package `import`, no new natyv mechanism. Children/slot-accepting components (`<Card>...</Card>`) need one shared callback type defined once in the base SDK (`sdk/go/widgets`, `type Builder func(parentID uint32) error` — raw id, **not** a `Container` param; confirmed against real source 2026-08-24 that `Container` is its own named `uint32` type with no implicit conversion to the `*uint32` `Layout.ParentID` every widget actually threads parent ids through; `error` return added when actually built, correcting this design note's own earlier omission) — never per-component — so a wrapper never needs to import a caller's package just to accept content. Go's (and Rust's crate-level) circular-dependency rule is package/crate-scoped, not intra-package/intra-crate, so reuse within one directory or one Rust crate (regardless of internal module nesting) is already safe with zero new machinery. The one irreducible case — two sibling feature packages each needing a component the other owns — is a real, unavoidable cycle at the language level; the fix is the standard one (extract the shared piece to a common leaf package), not a natyv workaround.

## CLI build flow

**Implementation language: the entire CLI (`prepare`, `build`, the future `get`) is Zig — no Go, no cross-language boundary.** `build`'s core mechanism is a real `zig build`/`@embedFile` invocation and `get`'s trampoline generation leans on Zig's own `@cImport`+comptime `@typeInfo` reflection — both irreducibly Zig-dependent regardless of what wraps them. A Go-CLI-shells-out-to-a-helper-binary design was considered and rejected: a binary that extracts and executes another embedded executable at runtime is a well-known malware dropper pattern, heavily scrutinized by AV/SmartScreen — a real distribution risk for a new, unestablished tool. A Zig CLI hosting a Go `prepare` parser as WASM via natyv's own existing Extism mechanism was also considered (avoids the dropper pattern, since WASM runs inside the host process, no separate executable ever hits disk) — but TinyGo's partial reflection/stdlib support is a real risk for reflection-heavy parser libraries, and the two things that motivated wanting Go (a mature parser library, strong concurrency for parsing multiple files) both turned out weak on inspection: `.ntx`/the stylesheet grammar is bounded enough that a hand-rolled recursive-descent parser (no reflection needed, any language) was already the right technique, and "parse N independent files in parallel" is embarrassingly parallel — well served by a plain `std.Thread` pool, which natyv-core already has proven experience with (`Io.Threaded`). Net: full Zig, one binary, one toolchain.

**Confirmed design, not yet implemented.** Three phases:
1. **`natyv prepare`** — codegen only (stylesheet + `.ntx` transpilation). Deterministic, natyv-owned, no compiler invocation. Any future binding-generator trampoline codegen for arbitrary dev-supplied C/Zig libraries must also live here, to keep this step (and everything downstream) never needing to touch a compiler or leave the dev's machine.
2. **Dev's own explicit compile step**, configured via a new required `conf.natyv.json` field (name TBD, e.g. `wasm_compile`) — a single command in the common case (matches real Extism PDK conventions: `tinygo build -o out.wasm -target wasip1 -buildmode=c-shared main.go` is already exactly this shape). Multi-step builds should point the field at a dev-authored script rather than natyv supporting shell chaining — avoids natyv ever needing to pick a shell/quoting convention across 3 OSes. Validated the same way `app_wasm` is validated today (`Config.zig`'s required-field pattern) — reject immediately, before spawning anything, if unset. Always surface the compile step's real stdout/stderr verbatim on failure, never swallow it into a generic message.

**`natyv build`'s freshness check is real and built (2026-08-24), confirmed design by Quinn**: `natyv build` is meant to be the one local-dev command that does everything (prepare -> wasm_compile -> bundle), while `natyv prepare` and the wasm-compile command stay independently runnable for CI pipelines that want them as separate, granular steps. ## Hosted signing service — architectural constraints

Business/legal/funding strategy for this lives outside this file (external memory) — the constraints below are the parts that shape how the CLI/build system itself must be built:

- **The entire build pipeline (`prepare`, the wasm compile, and `natyv build`'s bundling) must remain fully runnable by the dev locally, using only natyv's own open-source core** — producing a complete, working, *unsigned* binary must never require any hosted infrastructure. The only thing a paid hosted service ever does is **sign/notarize an already-fully-built binary**, using credentials the customer owns in a natyv-managed vault (mediated signing-request access only — never raw key export, matching the code-signing industry's real move toward HSM-backed keys).
- This means: **no natyv server-side component should ever need to receive a customer's source code or intermediate build artifacts** — only a finished binary, and only for signing. Don't design future features (e.g. the binding generator) in a way that requires source to leave the dev's machine.
- Real technical dependency this design rests on: natyv-core's own `build.zig` cross-compiling cleanly to all three target OSes from one host machine -- **confirmed for the compile step, 2026-08-27, and confirmed for real *running* behavior on both Windows and Linux via real VM tests, 2026-08-28/29** (see "Cross-compilation to Windows and Linux..." above). This architectural assumption is now fully load-bearing, not just compile-time.

## Binding generator (`natyv get`/`natyv bind`)

Scope confirmed 2026-08-24: a per-app-dev tool generating Extism host-function trampolines for a dev's *own* arbitrary C/Zig library — not natyv's own SDK generation — leaning on `@cImport`+comptime `@typeInfo` reflection for trampoline generation. **CLI surface confirmed 2026-08-25 as a two-command split: `natyv get` (declares one binding — writes/updates a `conf.natyv.json` entry, never generates anything) and `natyv bind` (generates — reads the config and produces bindings for whatever's missing or stale)** — mirrors `go get` (declare) vs. `go build`/`go mod tidy` (resolve); the earlier framing of a single renamed `natyv get` → `natyv bind` command was superseded by this split. `natyv bind` also runs as the first step of `natyv prepare`, so binding freshness is automatic everywhere `prepare` runs — including inside the LSP, which already reuses `prepare`'s own transpilation logic for virtual documents. **Sequencing, confirmed 2026-08-25: binding generator before LSP** — its core mechanism is a well-trodden Zig pattern, not the LSP's genuinely novel source-mapping problem, and it unlocks new real product surface rather than polishing something that already ships fine without it. **Test-library plan, confirmed same day**: a small hand-written fixture C lib first, then **zlib** as the first real-world proof case (small, stable, useful, moderate complexity, no callbacks/variadics), with **`libcurl` deferred, not rejected** (`curl_easy_setopt`'s true C-varargs signature is a legitimately hard case, but natyv already gets networking for free from Extism itself, so binding it proves generator robustness, not new product capability) and SQLite ruled out (already hand-written, proves little).

**Stage 1 is done (2026-08-25): comptime reflection + codegen proof against the fixture, verified via real compiles.** Plan at `~/.claude/plans/lexical-wishing-penguin.md`.

**Stage 2.1 is done (2026-08-25): config-driven generation, proven for real.** `src/bindgen/Reflect.zig`/`Codegen.zig` generalized away from Stage 1's hardcoded fixture allowlist — `Reflect.describe` now takes the `@cImport` namespace as a `comptime type` param, `Codegen.generate` takes `library`/`header` params driving per-entry names (`<library>_handle_table`, `<library>_c`, `package <library>`) instead of a hardcoded `"fixture"` string; proven generic via a real second test binding the same fixture functions under a distinctly-named `"widget"` library. `Config.zig` gained `BindingEntry`/`bindings` (externally-linked mode only for now — a second locally-vendored mode is a real, still-open future field set). New `src/cli/Bind.zig`: for each `bindings` entry, generates a small scratch Zig "reflector" program (comptime function list + a real `@cInclude`), writes it into `src/bindgen/` itself, and compiles+runs it as a real subprocess — the only way to turn a runtime-read config's function list into the comptime-known names `describe` requires. Two real findings while building this: `@import` rejects absolute paths outright (confirmed empirically), which is why the scratch reflector has to physically live in `src/bindgen/` as a real sibling of `Reflect.zig`/`Codegen.zig` rather than some temp location — `zig build-exe`'s own CLI argument accepts an absolute path fine, so once the scratch file's in the right place everything else is plain absolute strings; and the generated file's own `@cImport` alias had to become `pub` so `GeneratedFixtureCheck.zig`'s real native-callback test could reach the *same* translate-c instance instead of declaring an incompatible second one. Still explicitly not decided: where a generated Zig trampoline's real per-app destination is (Stage 2.2's job — see the plan file's own still-open architecture question). `zig build test -j1`: 63/63 steps, 460/460 tests passed (confirmed 3 times), `zig fmt --check` clean on every real source file.

**Real spike findings that corrected the original plan, before any generator code was written**:
- **Blind enumeration of `@typeInfo(cImportNamespace).@"struct".decls` doesn't work, confirmed empirically against this machine's real Zig 0.16.0.** Even a completely dependency-free fixture header produces a `cimport.zig` with platform-injected macro decls (`__nonnull` here) that fail to translate and become `@compileError` stubs; enumerating every decl forces evaluation of the broken ones too. Referencing a specific, comptime-known decl name (`@field(c, name)`) never touches them, since Zig's lazy analysis only evaluates what's actually named. **Design correction, not just a workaround**: the generator takes an explicit dev-authored allowlist of exact C function names to bind — matches Extism's own existing allowlist philosophy for network hosts.
- **A plain C enum collapses to a bare `c_uint` under translate-c** — `typedef enum {...} Status;` loses its named-variant grouping entirely by the time Zig sees it; each variant becomes its own top-level integer constant. Accepted Stage 1 scope: enum params/returns marshal as plain integers.
- Opaque handles, struct out-params, and C function-pointer (callback) params all reflect correctly once accessed by name: opaque pointers as `?*cimport.struct_X` (unwrap optional → pointer → `.@"opaque"`), struct out-params as `[*c]StructType` (unwrap → `.@"struct".fields`), callbacks as `?*const fn(...) callconv(.c) T` (unwrap twice more to the callback's own signature).

**What got built** (`src/bindgen/`): `Reflect.zig` (`@cImport`s the fixture, `describe(comptime name)` walks a named function via `@field`+`@typeInfo` into a plain-data `FnDescriptor` — deliberately fixed-capacity value arrays throughout, not slices into locals, after a **real segfault** from exactly that mistake during first implementation: a local array declared partway through `classify`'s call chain, returned as a slice, dangling once its frame returned — undefined behavior that happened to not crash in the smaller Reflect-only tests but did once Codegen's longer call chains disturbed the stack). `HandleTable.zig` (generic, fixed-capacity `id -> *T` registry — real C pointers can never cross the wasm boundary directly, so every opaque handle is really a bounded-table id, same discipline as `WidgetHost.zig`'s own slot registry). `Codegen.zig` (emits a Zig host trampoline + Go guest wrapper per function, matching `WidgetHostFunctions.zig`'s real 1-in-1-out-`ExtismVal`-JSON shape and `sdk/go/widgets/internal/value.go`'s real `//go:wasmimport`+`pdk.ResultBytes`/`ParamBytes` shape exactly; a generic path handles any function shaped like primitives/one-opaque-handle/one-struct-out-param, with a function name containing "destroy" additionally freeing its handle-table entry — a naming convention standing in for what the C type system can't express, same spirit as `ntx/Codegen.zig`'s own `on[A-Z]` convention; the `fixture_set_callback`/`fixture_trigger` pair gets a dedicated, explicitly non-generic emission, since a real C function pointer can't cross the boundary — the generated trampoline registers one real static `callconv(.c)` function with the C library itself, keyed by handle id via `user_data`).

**Stage 2 forward design, confirmed 2026-08-25 (not yet built)**: `conf.natyv.json` gains a top-level `bindings` array, one object per library (`{"library", "header", "include_dirs", "link", "functions"}` — `link` carries the real linker flags, e.g. `["z"]` for zlib, since the header alone never contains the library's actual compiled implementation; the exact field set may grow a second "locally vendored" mode, see below). `natyv get <target> [-zig|-c] --funcs=fn1,fn2 [--header=] [--include-dir=] [--link=]` only ever declares/updates one entry (re-running replaces its `functions` list wholesale, never merges); `natyv bind` only ever generates, and also runs as `natyv prepare`'s own first step so bindings freshness is automatic everywhere `prepare` runs (including the LSP, which reuses `prepare`'s own logic). `-zig <target>` must be a real URL (matches `zig fetch`/`go get` convention — no natyv-maintained name→URL table); `-c <target>` is either a bare name (pkg-config lookup against an already-installed system library) or a URL (fetch + vendor the raw C source). Mechanism: since a config's function list is only known at `natyv bind` run time but `@field(c, name)` needs `name` known at Zig compile time, `natyv bind` generates a small per-entry Zig "reflector" source (comptime function-name array + a real `@cInclude` of the entry's header) and compiles+runs it — exactly what `src/bindgen/dump_generated.zig` already does today for Stage 1's own hardcoded fixture, just generalized to read a real config entry.

**`natyv prepare --codegen`, confirmed 2026-08-25**: limits `prepare` to the stylesheet pipeline + `natyv bind` only — no `.ntx` transpilation, no `wasm_compile` (one flag covers both, since compiling can't meaningfully happen before `.ntx` output exists anyway). Flag-less `prepare` still does everything. Reasoning for excluding `.ntx` specifically, not just the compile step: running real `.ntx` transpilation on every fast-path call would write real `.natyv.go` files into the dev's guest directory speculatively/often, hurting codebase legibility and slowing down anything calling `prepare` frequently. **Important clarification this raised, not a contradiction with the LSP's own design**: the LSP's planned reuse of "prepare's transpilation logic" for `.ntx` virtual documents should call the underlying Zig functions directly, in-process, producing an in-memory buffer — it is not expected to shell out to the `natyv` CLI at all, so this flag and the LSP's own virtual-document generation are different invocation surfaces of the same underlying code, not competing for the same command.

**Vendoring a raw C library from a URL (`-c` + URL), confirmed 2026-08-25**: delegating to the library's own build system (`make`/`cmake`/`configure`) was considered and rejected *as the default* — those tools aren't guaranteed present the way Zig is (Windows especially), and unlike `wasm_compile` (a tool the dev already has, since they chose that guest language), a C library's build system is a transitive dependency imposed by whichever library gets picked, not something the dev signed up for. Resolved into three tiers: (1) **default** — compile every real `.c` file found in the vendored tree directly via Zig's own C toolchain, zero extra dependency, matching `vendor/freetype`/`vendor/sdl_ttf`/`vendor/clay`'s own existing precedent (same accepted limitation carried over too: a library with build-time-config-gated optional dependencies may need hand-curation, same as FreeType needs today); (2) **opt-in `c_build` config field**, mirroring `wasm_compile` exactly, for a dev who explicitly wants to delegate — a missing tool surfaces via the same real-stdout/stderr-verbatim, natyv-attributed convention `Compile.zig`/`Validate.zig` already use, so only a dev who opted in ever hits it, and clearly; (3) **escape hatch** — the dev builds it themselves however they already do, points `natyv get -c` at the already-compiled artifact + header + link flags directly.

**What "can't translate" actually means, empirically tested against real Zig 0.16.0 (Aro-based translate-c) rather than assumed — corrects the original, too-pessimistic framing**: the real dividing line is **"is the macro's body a single C expression?"**, not "is it a macro." Any single-expression macro — object-like constants, one macro referencing another, a compound-literal struct initializer, a variable alias, and **function-like macros with a one-expression body (including a ternary)** — translates into a real, callable `pub const`/`pub inline fn`. Only token-pasting (`##`), stringification (`#x`), and non-expression bodies (`do{}while(0)`, multi-statement `{...}`) fail, plus a handful of narrow literal-suffix/attribute tokens mostly seen only in system compat headers. The `zig translate-c` pre-pass above needs to encode this real rule, not a blanket "any macro fails" one. **A real, related bug found and fixed the same session**: a function-like macro that does translate becomes a *generic* Zig function (`anytype` params/return, confirmed via `@typeInfo(...).@"fn".is_generic == true` with every param `.type`/`.return_type` being `null`) — unwrapping either with `.?` is a real, reproducible crash (triggered on purpose before it could ever reach a real dev's config). Fixed in `src/bindgen/Reflect.zig`'s `describe`: checks `fn_info.is_generic` and returns a new `error.GenericFunction` immediately. natyv deliberately does not support binding a generic/macro-derived function at all — matches Quinn's own "simplify the binding to C code as much as possible" call: the dev writes a small real C wrapper function around the macro instead, rather than natyv requiring concrete argument types just to make one macro bindable. Regression-tested via a deliberately-unlisted `#define FIXTURE_DOUBLE(x) ((x) * 2)` in the fixture header. `zig build test -j1`: 61/61 steps, 456/456 tests passed.
